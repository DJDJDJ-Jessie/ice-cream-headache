# QQ 宠物桌面企鹅复刻开发文档

## 1. 开发目标

开发目标是把当前仓库中的 QQ 宠物相关资源，整理、验证并移植为 Windows 10/11 上可运行的桌面企鹅 `.exe`。

开发不再以“先做出功能”为优先，而以“先对齐原版”为优先。

## 2. 当前仓库判断

当前仓库主要包含：

- 已打包网页入口：`index.html`、`static/*`
- Ruffle 运行时：`Ruffle/*`
- QQ 企鹅 SWF 动作资源：`Penguin/GG/*`
- 钓鱼小游戏资源：`fishing/*`
- LayaAir 子项目资源：`sub/*`
- 当前桌宠移植代码：`desktop/*`

当前桌宠代码位于：

```text
desktop/main.js
desktop/pet.html
desktop/pet.css
desktop/pet.js
desktop/preload.js
```

## 3. 关键技术判断

### 3.1 不能继续依赖“反复加载单个 SWF”作为最终方案

当前闪屏的根因是：桌宠代码把每个动作 SWF 当作独立文件加载。Ruffle 在加载单个 SWF 时可能显示自己的 preloader/logo，并且每次切换都触发加载流程。

原版更可能是：

- 一个 Flash 主控程序长期运行。
- 主控程序提前加载动作资源。
- 动作切换发生在同一个 Flash 舞台、MovieClip 或时间轴内部。

因此开发路线必须优先验证：

1. `common.swf` 是否是原主控或关键共享资源。
2. `index.html`/打包 JS 是否已有完整动作调度逻辑。
3. `sub/main.min.js` 是否包含更接近原版的动作状态机。
4. 如果无法复用主控，则转向 SWF 转帧动画/精灵图播放。

### 3.2 Ruffle 只能作为过渡方案

Ruffle 可以帮助快速验证 SWF 资源，但不保证一比一还原老 Flash ActiveX 的透明、缓存、切换和性能表现。

最终可选路线：

| 路线 | 说明 | 优先级 |
| --- | --- | --- |
| 复用原 Flash 主控 | 找到 `common.swf` 或原脚本入口，让一个播放器长期运行 | 最高 |
| SWF 转帧/精灵图 | 把动作变成可控 Canvas 动画，彻底消除 Ruffle 加载闪屏 | 高 |
| Ruffle 多播放器缓存 | 每个动作一个常驻播放器，只切可见性 | 中 |
| 当前双播放器加载 | 过渡止血方案 | 低 |

## 4. 开发原则

1. 先验证资源，再接入主流程。
2. 未确认动作不得进入随机行为。
3. 未确认原版文案不得出现在运行界面。
4. 闪屏、Logo、加载层属于阻断问题，不能视为可接受体验。
5. 每次开发结束必须更新进度百分比。
6. 每次生成 `.exe` 后必须说明路径。
7. 每个阶段必须有可验证的验收标准。

## 5. 开发阶段规划

### 阶段 A：资源审计

目标：

- 确认所有 SWF 的用途。
- 确认是否存在原版主控。
- 确认现有网页包里是否已有可复用状态机。

任务：

- 列出所有 SWF、FLA、JSON、JS 资源。
- 分析 `common.swf`。
- 分析 `static/js/main.*.js` 中的 QQPet 逻辑。
- 分析 `sub/main.min.js` 中的 LayaAir 逻辑。
- 建立资源来源和用途表。

验收：

- `docs/action-map.md` 中每个动作都有状态：confirmed / guessed / unused / unknown。
- 明确技术路线：复用主控、播放器缓存、或转帧动画。

### 阶段 B：无闪动作播放

目标：

- 动作切换时不出现 Ruffle Logo、加载层、白底、黑底。
- 默认待机和手动动作稳定。

任务：

- 验证原 Flash 主控路线。
- 如果主控不可用，做动作播放器缓存。
- 如果缓存仍闪，做 SWF 转帧实验。
- 建立自动视觉检查：截图中不得出现 `ruffle` 字样。

验收：

- 连续切换 20 次已确认动作，无明显加载闪屏。
- 桌面只显示企鹅和原版 UI。

### 阶段 C：原版桌面交互

目标：

- 还原桌面宠物的基础行为。

任务：

- 左键拖拽。
- 拖拽动作和落地动作。
- 右键菜单结构。
- 托盘图标。
- 状态入口。
- 空闲行为。
- 屏幕边界行为。

验收：

- 不出现普通窗口感。
- 不出现模拟 XP 桌面。
- 交互入口与原版资料一致。

### 阶段 D：原版 UI

目标：

- 还原右键菜单、状态面板、气泡、食品/日用品/药品入口。

任务：

- 收集原版截图或旧客户端画面。
- 建立 UI 截图参考库。
- 只按参考图实现。

验收：

- 每个 UI 面板都有参考来源。
- 没有自创现代 UI。

### 阶段 E：养成规则

目标：

- 还原核心养成系统。

任务：

- 饥饿、清洁、心情、健康。
- 成长、等级。
- 元宝。
- 食品、日用品、药品。
- 生病、吃药、死亡或濒危机制。
- 学习、打工收益。

验收：

- 每个数值变化有来源或明确标注为近似。
- 本地存档稳定。

### 阶段 F：小游戏与社区入口

目标：

- 整合已有钓鱼小游戏和其他可复刻入口。

任务：

- 分析 `fishing/*`。
- 决定小游戏是独立窗口、原版窗口还是桌宠菜单入口。
- 还原收益和消耗。

验收：

- 小游戏入口不破坏桌宠体验。
- 能从桌宠自然进入并返回。

## 6. 当前优先级

当前最高优先级：

1. 资源审计。
2. 动作映射准确化。
3. 解决闪屏。
4. 再做右键菜单和 UI 还原。
5. 最后做养成规则。

暂停事项：

- 暂停继续发明功能。
- 暂停随机动作。
- 暂停新增自创文案。
- 暂停现代化状态面板。

## 7. 验证命令

运行桌宠：

```powershell
npm run start:pet
```

打开动作查看器：

```powershell

```

生成便携式 `.exe`：

```powershell

```

生成完整 Windows 构建：

```powershell
npm run build:win
```

## 9. 风险清单

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| Ruffle 切换 SWF 闪屏 | 破坏桌宠体验 | 优先验证主控 SWF；不行则转帧动画 |
| 原版资料不足 | 动作和数值无法一比一 | 所有未确认内容标记为 guessed，不进正式随机行为 |
| SWF 透明兼容差 | 出现底色或 Logo | 视觉检查，不达标则放弃直接播放 |
| 菜单/UI 缺截图 | 容易现代化跑偏 | 先收集参考，再实现 |
| 养成公式缺失 | 数值不可信 | 暂用近似时明确标注 |
| 打包体积大 | exe 较大 | 后期再做资源裁剪，不影响早期准确性 |
